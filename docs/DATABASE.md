# NUSAQUEST Database

Database mode turns on when `DATABASE_URL` is set (`docker compose up` does this for you).
Without it the app runs in memory mode: no accounts, quizzes in the browser, nothing
persisted (see `docs/ARCHITECTURE.md` → Runtime modes).

Stack: PostgreSQL 17 · [Drizzle ORM](https://orm.drizzle.team) (`drizzle-orm` + `pg`) ·
SQL migrations generated by `drizzle-kit` and committed in `drizzle/`.

```
lib/db/
  schema.ts               tables, constraints, indexes (THE source of truth)
  client.ts               getDb() / checkDb() / closeDb(): one pg Pool per process
  migrate.ts              runMigrations(): applies drizzle/*.sql on boot
  users.ts                accounts (admin / lecturer)
  auth-sessions.ts        sign-in sessions (token hashes)
  quizzes.ts              listQuizzes / getQuiz / saveQuiz / deleteQuiz (owner-scoped)
  session-persistence.ts  write-behind of live games (SessionPersistence for the runtime)
  reports.ts              listHostSessions / getSessionEngineState (history, analytics)
  errors.ts, ids.ts       pg error codes, uuid helpers
lib/auth/                 password hashing, cookie sessions, lecturer resolution, admin actions
lib/server/bootstrap.ts   ensureServerReady(): migrations → first admin → seeds → restore games
drizzle/                  generated SQL + drizzle-kit snapshots (commit these)
drizzle.config.ts         drizzle-kit settings
```

## Schema

```
users ─┬─< auth_sessions
       ├─< quizzes ──< questions ──< answers
       ├─< media
       └─< game_sessions ─┬─< players ──< player_answers
            (quiz_id → quizzes, set null)  ├─< leaderboard_snapshots
                                           └─< session_events
```

| Table                   | What it holds                                                                                                                                | Notes                                                                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `users`                 | Lecturers and admins: email, scrypt `password_hash`, name, salutation, `role` (`admin` \| `lecturer`), `locale`, `disabled`, `last_login_at` | Email is unique and must be lowercase (check constraint).                                                                            |
| `auth_sessions`         | One row per signed-in device: `token_hash` (sha256 of the cookie), `expires_at`, `last_seen_at`, `user_agent`                                | Deleted on sign-out, password reset and when an account is disabled.                                                                 |
| `quizzes`               | An "arena": title, course fields, topic, difficulty, language, visibility, mode                                                              | Always read and written with `owner_id` in the WHERE clause; that filter _is_ the authorization.                                     |
| `questions`             | Ordered by `position`; `type`, prompt, media, `time_limit` (preset seconds), `points` (0–10 000), `metadata` jsonb                           | `metadata` holds `acceptedAnswers` (short answer) and `numeric` (value, tolerance, unit).                                            |
| `answers`               | Options per question, ordered by `position`, with `is_correct`                                                                               | Never sent to players before the reveal.                                                                                             |
| `game_sessions`         | One row per hosted game: `room_code`, `status`, `current_question`, `quiz_snapshot` (the quiz frozen at start), `engine_state`, `meta`       | `id` is the engine's session id (text). Unique `room_code` among live rooms only (partial index on `status in ('lobby','running')`). |
| `players`               | Normalized copy of each player's final numbers                                                                                               | Primary key `(session_id, id)`: simulated players reuse fixed ids.                                                                   |
| `player_answers`        | One row per player per question: payload, `is_correct`, points, response time                                                                | Unique `(session_id, player_id, question_id)`; `is_correct` is null until the reveal.                                                |
| `leaderboard_snapshots` | Leaderboard after each revealed question                                                                                                     | Unique `(session_id, question_index)`.                                                                                               |
| `session_events`        | Phase changes (`type = 'phase'`, `{from, to, questionIndex, players}`)                                                                       | Append-only timeline for audits.                                                                                                     |
| `media`                 | Uploaded image files (the bytes live in `UPLOAD_DIR`)                                                                                        | `file_name` is random and unique.                                                                                                    |

Enumerations are `text` + `CHECK` constraints instead of Postgres enums: adding a value is a
one-line migration, and the schema stays portable.

### What `game_sessions.engine_state` contains

The complete `PersistedAuthority` of `lib/realtime/authority.ts` minus `engine.quiz` (which is
stored once, in `quiz_snapshot`): phase, question index, deadlines, every player, every
answer, every reveal, the leaderboard, and `tokens` (player id → **sha256** of the player's
bearer token; raw tokens never reach the database). That is enough to restore a running game
after a restart; `getSessionEngineState()` rebuilds the full `EngineState` for analytics.

`players`, `player_answers` and `leaderboard_snapshots` are _derived_ copies for SQL
reporting. They are written with idempotent upserts whenever a question is revealed and when a
game finishes or is ended, so writing the same state twice (or after a restart) never
duplicates rows.

## How startup works

1. `instrumentation.ts` → `register()` runs once when the Node server starts and awaits
   `ensureServerReady()` (`lib/server/bootstrap.ts`). Every API route also awaits it; after the
   first call that is free.
2. **Migrations**: `runMigrations()` applies every file in `drizzle/` not yet recorded in
   `drizzle.__drizzle_migrations`. A Postgres advisory lock makes concurrent boots (a rolling
   restart) wait for each other instead of migrating twice.
3. **First admin**: only when the `users` table is empty _and_ `ADMIN_EMAIL` +
   `ADMIN_PASSWORD` are set (password ≥ 8 characters), an `admin` account is created
   (`ADMIN_NAME`, default "Administrator") and receives the five demo quizzes. Later boots
   never touch accounts: changing `ADMIN_PASSWORD` afterwards does **not** reset anything.
4. Expired sign-in sessions are purged.
5. The game runtime switches to Postgres persistence and restores unfinished, unexpired
   sessions. Rooms whose PIN expired are marked `ended`, which releases their room codes.

If Postgres is unreachable at boot, the error is logged, the server still starts, and the
database steps are retried on a later request (at most every 15 s). Check
`GET /api/health` (`db: "up" | "down"`) and `docker compose logs app`.

The shared classroom demo (`/host/session/demo`, PIN `482913`) is never persisted.

## Changing the schema (migrations workflow)

1. Edit `lib/db/schema.ts`.
2. Generate the SQL:

   ```sh
   npx drizzle-kit generate --name add_quiz_tags
   ```

   This writes `drizzle/NNNN_add_quiz_tags.sql` plus a snapshot in `drizzle/meta/`. No
   database connection is needed.

3. Read the generated SQL. Adjust it by hand only when needed (e.g. a data backfill), keeping
   the `--> statement-breakpoint` separators.
4. Run the integration tests against a throwaway Postgres (below), then **commit `drizzle/`
   together with `schema.ts`**.
5. Deploy. The app applies the new migration on its next start.

Rules of thumb:

- Never edit or delete a migration that has been deployed; add a new one.
- Make destructive changes in two releases: first stop using the column, then drop it.
- A new `NOT NULL` column needs a default (or a backfill in the same migration).
- `npx drizzle-kit check` validates the migration history; `npx drizzle-kit migrate`
  (with `DATABASE_URL` set) applies migrations manually, e.g. from a maintenance shell.

## Accounts and sign-in

- Passwords: Node's built-in scrypt (N=16384, r=8, p=1, 64-byte key, 16-byte random salt),
  stored as `scrypt$16384$8$1$<salt>$<hash>` and compared in constant time. Unknown emails are
  checked against a dummy hash so timing does not reveal which addresses exist.
- Sessions: a random 256-bit token in the `nq_session` cookie (HttpOnly, SameSite=Lax, Path=/,
  14 days); only its sha256 is stored. `SESSION_COOKIE_SECURE=auto` (default) marks the cookie
  `Secure` when the reverse proxy reports `X-Forwarded-Proto: https`; set `true` behind HTTPS
  you control, `false` only for plain-HTTP classroom LANs.
- Failed sign-ins are throttled in memory, each per 15 minutes: 5 per email + IP, 30 per IP,
  and 20 per email from any address (a client that spoofs its address gains no extra
  guesses; `lib/auth/login-throttle.ts`).
- Admins manage accounts in **Pengaturan → Akun dosen**: create lecturers (a temporary
  password is shown once), disable/enable (disabling signs the account out everywhere), and
  reset passwords. Every signed-in lecturer can change their own password in
  **Pengaturan → Kata sandi**. The last active admin cannot be disabled.
- Locked out of every admin account, or need bulk changes? Use the server-shell tool, which
  hashes with the same scheme inside the app container and writes with psql:

  ```sh
  bash deploy/users.sh list
  bash deploy/users.sh reset-password admin@example.ac.id     # prompts; signs the user out everywhere
  bash deploy/users.sh add dosen@example.ac.id "Nama Dosen" lecturer
  ```

## Backups

Everything durable lives in two places: the Postgres volume (`pgdata`) and the uploads
volume (`uploads`, mounted at `UPLOAD_DIR`). Back up both.

```sh
bash deploy/backup/backup.sh     # → ./backups/nusaquest-<ts>.dump (pg_dump -Fc) + uploads-<ts>.tar.gz
```

Underneath it is a plain logical dump, which is consistent while the app keeps running:

```sh
docker compose exec -T db sh -c 'pg_dump -Fc --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' > nusaquest.dump
```

Schedule it with cron or `deploy/systemd/nusaquest-backup.timer`, or run
`docker compose --profile backup up -d` for the looping backup container. Create `./backups`
as the deploy user first (`mkdir -p backups && chmod 700 backups`, see docs/DEPLOYMENT.md §8).
Copy the backups off the VM (Proxmox Backup Server, rsync to another
host, …); a backup on the same disk is not a backup.

Restore (stops the app, replaces all tables in one transaction, starts the app again):

```sh
bash deploy/backup/restore.sh backups/nusaquest-20260928T190000Z.dump backups/uploads-20260928T190000Z.tar.gz
```

Test a restore every semester. A dump from an older release restores fine: the app migrates
it forward on start. Restoring a _newer_ dump into an older release is not supported.

Housekeeping (retention under UU PDP No. 27/2022): old games can be removed with their
players, answers, snapshots and events in one statement, since those tables cascade from
`game_sessions`. Live rooms are never touched. Replace `12 months` with the retention period
agreed with BINUS (the same statement is in `docs/DEPLOYMENT.md` §8, wrapped for
`docker compose exec`):

```sql
delete from game_sessions where status in ('finished', 'ended') and created_at < now() - interval '12 months';
```

## Integration tests

The repository functions, migrations, session persistence and bootstrap are tested against a
real Postgres. Tests create (and drop) their own database per file, and are skipped when
`TEST_DATABASE_URL` is unset, so `npm test` needs no database.

```sh
docker start nq-test-pg 2>/dev/null || docker run -d --name nq-test-pg \
  -e POSTGRES_USER=nq -e POSTGRES_PASSWORD=nq -e POSTGRES_DB=nusaquest_test -p 55432:5432 postgres:17-alpine
TEST_DATABASE_URL=postgres://nq:nq@localhost:55432/nusaquest_test npx vitest run tests/unit/db
```

## Switching to another SQL engine

Postgres is the supported engine. Postgres-compatible servers (e.g. a campus-managed
PostgreSQL cluster, YugabyteDB) work unchanged: point `DATABASE_URL` at them.

Drizzle also supports MySQL/MariaDB and SQLite, but NUSAQUEST uses a few Postgres features, so
a port is a deliberate project, not a configuration change:

| Area                                   | Postgres feature used                                                                                                                                       | Port notes                                                                                                                                                                                     |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lib/db/schema.ts`                     | `pgTable`, `uuid … defaultRandom()`, `jsonb`, `timestamptz`, identity column, `CHECK`s                                                                      | Rewrite with `mysql-core` / `sqlite-core`: `varchar(36)` + app-generated uuids, `json`, `datetime`/integer timestamps, auto-increment.                                                         |
| Live room codes                        | Partial unique index `… where status in ('lobby','running')`                                                                                                | MySQL has no partial indexes: use a generated column (`room_code` when live, else NULL) with a unique index. SQLite supports partial indexes.                                                  |
| `session-persistence.ts`, `reports.ts` | `on conflict … do update` with `excluded.*`, `select … for update`, jsonb operators (`->`, `->>`, `jsonb_each`, `jsonb_array_elements`) in the report query | MySQL: `on duplicate key update`, `JSON_EXTRACT`/`JSON_TABLE`; SQLite: `json_each`, no row locks (single writer). Consider computing report numbers in TypeScript from `engine_state` instead. |
| `migrate.ts`                           | `pg_advisory_lock` around migrations                                                                                                                        | MySQL `GET_LOCK()`; SQLite needs none.                                                                                                                                                         |
| `client.ts`                            | `pg` Pool + `drizzle-orm/node-postgres`                                                                                                                     | `mysql2` + `drizzle-orm/mysql2`, or `better-sqlite3` + `drizzle-orm/better-sqlite3` (a new dependency).                                                                                        |
| `drizzle/`                             | Postgres SQL                                                                                                                                                | Start a fresh migration history (`dialect` in `drizzle.config.ts`), then move data with a one-off export/import script.                                                                        |

The rest of the app talks to `lib/db/*` functions only (never to SQL), so a port stays inside
`lib/db/` plus `drizzle.config.ts`.
